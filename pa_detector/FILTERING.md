# 458件をどう絞るか

## まず1件バグを直しました

`run_intraday.py` を差し替えてください。

擬似指数のリターン計算で、**日付が昇順に並んでいない系列に `pct_change()` を適用**
していました。`pd.concat(axis=1)` が返すインデックスは銘柄ごとの日付の和集合で、
昇順である保証がありません。結果として、隣り合わない日付どうしの差分を
取っていました（2023年の日付と2025年の日付を比べているような状態）。

型17（逆行高）はこの指数リターンを使うので、**誤った判定をしていました**。
日付でソートしてから計算するよう修正し、指数リターンが正しくなること、
βの中央値が0.79と妥当な範囲に入ることを確認しています。

## 0件だった4つの型について

いずれも異常ではありませんでした。

| 型 | 否定度 | 0件の理由 |
|---|---|---|
| 型11 フォールスブレイクダウン | 3位 | 40日安値の更新が条件。旧DBでは17件出るので検知器は正常。8月21日はたまたま該当なし |
| 型15 分散の否定 | 4位 | 条件が4段構え（20日高値更新→出来高1.5倍→分散日→薄商いの押し目）。極端に稀 |
| 型17 逆行高 | 9位 | **指数下落日にしか発火しない設計**。市場が上げた日は構造的に0件 |
| 型6 マルボウズの否定 | 13位 | 前提となる形（ヒゲのない大陰線）自体が稀 |

型17が0件だったのは、8月21日に市場が上昇していたためと考えられます。
下落日には出てくるはずなので、しばらく様子を見てください。

## 絞り込みの選択肢（実データで計算）

| 案 | 設定 | 件数 | 実銘柄数 |

### 推奨は D 案

```bat
set PA_EXCLUDE=13,3,14,7,8,16,4
set PA_CONF_B=1.0
```

**117件／104銘柄。** 理由は3つあります。

第一に、**除外する型は解説書の順位で下位に置いたものと一致**しています。
事後的に「多いから切る」のではなく、事前の理屈と実測が一致した結果です。
型13（99件）と型3（91件）で全体の41%を占めており、
順位表で「発生頻度が高すぎて希少性がない」と予測したとおりでした。

第二に、**余裕1.0という閾値には意味があります**。ATR1個ぶん、つまり
その銘柄の平常の1日の値動きを超えて基準線から離れている、ということです。
中途半端な奪回を落とせます。

第三に、**上位群の型を全部残せます**。型9・型10・型18・型12・型5・型1 は
そのまま出るので、否定度の高いシグナルを取りこぼしません。

### F案（82件）にする場合

否定度上位5型だけに絞る案です。より少なく、より原理に忠実。
ただし型5（ヒゲ高値の終値抜け、49件）や型12（ネックライン奪回、25件）が
落ちるので、拾える機会は減ります。

**まずD案で1〜2週間見て、それでも多ければF案**、という進め方を勧めます。

## 型18が64件と多いことについて

これは**季節要因**なので、絞る対象ではありません。

8月21日から15営業日以内に第1四半期決算が集中しています
（7月末〜8月上旬）。型18は「決算反応日の高値を15日以内に奪回」なので、
決算期の直後は必然的に増えます。11月や2月にも同じ山が来ます。

気になるようなら `k` を15日から10日に縮められますが、
決算後の株価が落ち着くには2〜3週間かかることを考えると、
15日は妥当な設定だと思います。

## 設定の当て方

`run_pa_eod.bat` の絞り込みブロックを書き換えてください。

```bat
rem --- 絞り込み ---
set PA_MIN_TURNOVER=100000000
set PA_CONF_B=1.0
set PA_EXCLUDE=13,3,14,7,8,16,4
```

`PA_MIN_TURNOVER` を1億円に上げると、1,440銘柄がさらに減ります。
上の117件はこれを5,000万円で計算した数字なので、
1億円にすればもう少し減るはずです。

試すときは環境変数を打ってから `--dry-run` で件数だけ見るのが早いです。

```
set PA_EXCLUDE=13,3,14,7,8,16,4
set PA_CONF_B=1.0
python -m pa_detector.run_intraday --eod --dry-run
```

## 除外した型を捨てないでください

`PA_EXCLUDE` で外した型も、**検証の対象としては残す価値があります**。

いま外すのは「メールに載せると多すぎるから」であって、
「効かないと確認できたから」ではありません。第9章の尤度比を推定すれば、
型13が本当に無情報なのか、それとも件数が多いだけで優位性はあるのかが分かります。

日次CSVには除外前の全ヒットを残す設定にもできるので、
検証を始める段階になったら言ってください。
