# 「遅れて検知している」問題の修正

ご指摘のとおりでした。**型10が8月7日のブレイクを8月21日にも報告していた**のは、
私の設計ミスです。

差し替えるファイルは `patterns.py` と `run_intraday.py` の2つです。

---

## 何が起きていたか

型10の判定条件は、これだけでした。

```python
if ctx.c <= h_prev:      # 前回高値を終値で上回っているか
    return None
```

**時間の条件が入っていません。** 一度上抜けると、株価がその水準より上にある限り
毎日発火し続けます。旧DBで実測したところ、こうなっていました。

```
  6479  22/30日  ●●●●●●●●●●●●●●●●●●●●●●········
  8035  19/30日  ●●●●●●●●●●●●●●●●●●●···········
  6861  18/30日  ●●●●●●●●●●●●●●●●●●············
```

最長22営業日連続です。1か月前のイベントが今日の一覧に載っていました。

原因は解説書 第8章の記述にあります。型10の判定条件に

> 否定：C > その前のスイング高値。**時間窓は設けず、更新した事実で判定してよい**

と書きました。理屈としては間違っていませんが、**日次スクリーニングの仕様としては誤り**です。
一回きりのイベントが、継続する状態に化けてしまいます。

---

## 型10だけの問題ではありませんでした

全型で「直近20営業日のうち何日発火したか」を測ったところ、こうなっていました。

| 型 | 平均発火日数 | 最長 |
|---|---|---|
| 型3 Fill and Go | 5.0日 | 15日 |
| 型12 ネックライン奪回 | 4.8日 | 12日 |
| 型10 高値切り下げの否定 | 4.7日 | 14日 |
| 型13 移動平均への復帰 | 4.2日 | 11日 |
| 型5 ヒゲ高値の終値抜け | 2.9日 | 9日 |
| 型9 スプリング | 2.4日 | 6日 |

**根本原因は共通**です。回復条件「終値 > 基準線」はいったん成立すると
その後も真であり続け、さらに逸脱側にも k 日の猶予があるため、
同じ銘柄・同じ型が連続して報告されます。

なお、この事実は先日の「型13が99件、型3が91件」という偏りの主因でもありました。
あれは「その型が出やすい」のではなく、**過去のヒットが積み上がっていた**のです。

---

## 修正

個別に直すのではなく、全型に一律の仕組みを入れました。

**前営業日までのデータでも同じ型が成立していたなら、報告しない。**

`detect_all()` に `prev_ctx`（前日までのデータで作った判定文脈）を渡すと、
同じ検知器を前日時点でも走らせ、そこで既に成立していた型を除外します。

否定PAは「その日に起きたイベント」であって「継続する状態」ではないので、
初日だけを報告するのが正しい仕様です。

### 修正後

| 型 | 平均発火日数 | 最長 |
|---|---|---|
| 型3 | 1.7日 | 4日 |
| 型13 | 1.6日 | 5日 |
| 型12 | 1.6日 | 3日 |
| 型9 | 1.4日 | 4日 |
| **型10** | **1.2日** | **2日** |

全型が1.0〜1.7日に収まりました。残る1超は「一度崩れて再度ブレイクした」という
正当な再発火であって、状態の継続ではありません。

## 件数への影響

旧DB（491銘柄）での比較です。

```
修正前 144件 → 修正後 64件
```

**約56%が「過去に検知済みの継続」でした。**

型別の偏りも解消しています。

| 型 | 修正前 | 修正後 |
|---|---|---|
| 型13 | 99件 | 6件 |
| 型3 | 91件 | 8件 |
| 型10 | 36件 | 2件 |

プライム1,558銘柄での458件も、同様に200件前後まで減ると見込まれます。

## 絞り込みの方針を変えます

前回お渡しした FILTERING.md の推奨（型13・型3などを除外する案）は、
**この修正で前提が変わりました。**

あの提案は「型13と型3が全体の41%を占めている」という観測に基づいていましたが、
その偏りはバグによるものでした。除外の根拠が消えたことになります。

**まず何も除外せずに走らせて、実際の件数を見てください。**

```
set PA_EXCLUDE=
set PA_CONF_B=0.5
python -m pa_detector.run_intraday --eod --dry-run
```

200件前後に収まるようなら、そこから `PA_CONF_B=1.0` で半分程度に絞る、
という順序が妥当です。型を除外するのは、それでも多い場合の最後の手段にしてください。

事前の順位表に基づく除外（否定度下位を切る）は理屈としては筋が通りますが、
**今回のように観測が汚れている状態で判断すると誤ります**。
まず正しい観測を得るのが先です。

---

## 検証への影響

この修正は、第9章の尤度比の推定にも効きます。

修正前は同じイベントが何度もカウントされるため、
「検知された銘柄群のリターン」を計算すると**同一イベントを重複して数える**ことになり、
標本の独立性が崩れていました。有意性を過大評価する方向に働きます。

初日だけを報告する仕様に変えたことで、1イベント1標本になり、
検証の前提が整いました。
